# I-Digital SMS через REST в Home Assistant

Этот рецепт добавляет YAML-действия `rest_command.idigital_sms_send`,
`rest_command.idigital_sms_status` и native HA script `script.idigital_sms_send`.
Script принимает получателя и текст при каждом запуске и возвращает компактный
результат вызывающей automation/script. Это ограниченный способ отправки, а не законченная интеграция:
он не проверяет мобильный номер, не ограничивает частоту и не защищает от
повторного вызова. Не подключайте отправку к автоматизации, которая может
повторно запускать действие при таймауте.

## Настройка

Скопируйте оба раздела (`rest_command:` и `script:`) из
[sms_rest_commands.yaml](sms_rest_commands.yaml) в один пакет HA. Если пакеты
не настроены, добавьте соответствующие разделы в `configuration.yaml`.
В локальном `/config/secrets.yaml`
добавьте:

```yaml
idigital_sms_authorization: "Basic <API-ключ-I-Digital-в-готовом-виде>"
```

Вместо текста в угловых скобках подставьте значение из I-Digital, уже
закодированное провайдером для HTTP Basic. Не кодируйте его повторно и не
вставляйте в сам рецепт. Ограничьте доступ к `/config` и его резервным копиям.
Этот ключ разрешает отправку за счёт баланса аккаунта; бесплатный режим не
предполагается и здесь не проверен.

Проверьте конфигурацию Home Assistant и перезагрузите YAML-интеграцию
RESTful Command через действие `rest_command.reload` (или перезапустите HA).
До реальной отправки проверьте правила тестового аккаунта, доступность имени
отправителя, возможную стоимость и номер, на который разрешена тестовая
отправка. В issue #17 указана информация пользователя об одном бесплатном
номере, но это ограничение аккаунта сейчас не подтверждено.

## Вызов одного SMS действия

Direct API принимает массив объектов даже для одиночного сообщения. Recipe
сериализует ровно один объект с `channelType`, `senderName`, `destination` и
`content`; это совпадает с фактическим payload в
`/root/smsforcrm/backend/idigital.py` и тесте
`/root/smsforcrm/backend/tests/test_idigital.py`.

Используйте `script.idigital_sms_send`, передайте один E.164 номер с `+` или без
него и текст. Script fields показываются в UI HA; в automation вызывайте action
напрямую, чтобы дождаться результата. Не используйте `script.turn_on`, если
нужно получить response.

```yaml
actions:
  - action: script.idigital_sms_send
    data:
      target: "+7XXXXXXXXXX"
      message: "Дверь открыта"
    response_variable: sms_result
```

Script возвращает одно из трёх состояний:

- `accepted` — HTTP 200, `errors: false` и ровно один `messageUuid` в ответе;
- `rejected` — Direct API вернул HTTP 4xx или тело с `errors: true`, либо поля
  ввода пустые/содержат разделители нескольких получателей;
- `unknown` — timeout/сбой без ответа, HTTP 5xx, неожиданный JSON или ответ без
  ровно одного UUID. Считайте `unknown` неоднозначным результатом: провайдер мог
  принять SMS до сетевого сбоя.

При `accepted` в ответе есть `message_uuid`, его можно передать в status action.
Пример обработки ответа:

```yaml
actions:
  - if: "{{ sms_result['status'] == 'accepted' }}"
    then:
      - variables:
          sms_message_uuid: "{{ sms_result['message_uuid'] }}"
```

`accepted` означает только приём Direct API, не доставку на телефон. Не
повторяйте `script.idigital_sms_send` автоматически при `unknown`; сначала
сверьте статус или историю провайдера, затем создайте отдельный новый вызов.

## Проверка доставки

Передайте UUID из успешного ответа в `rest_command.idigital_sms_status`:

```yaml
actions:
  - action: rest_command.idigital_sms_status
    data:
      message_uuid: "UUID-из-ответа-провайдера"
    response_variable: sms_status_response
```

Проверяйте `sms_status_response['status']` и поле `status` в JSON провайдера.
Значение `delivered` подтверждает статус доставки, `undelivered` или другой
финальный ошибочный статус — недоставку, а `queued`/`sending` — ожидание.
HTTP 404, сетевой сбой или неизвестный ответ не доказывают доставку; не
повторяйте POST автоматически. Запрос статуса безопасно повторить отдельно.

## Пределы этого рецепта

- Один номер передаётся в каждом вызове, но шаблон не валидирует, что это
  действующий мобильный E.164 номер. Direct API вернёт ошибку на неверный
  формат/получателя.
- `mode: single` блокирует только одновременный запуск пока script ждёт ответ;
  он не ограничивает частоту следующих вызовов. Нет постоянного журнала попыток,
  идемпотентности, лимита частоты или явного подтверждения конкретных номера и
  текста.
- Ключ хранится как секрет HA, но пользователь вводит отправителя и ключ не
  через UI интеграции. Для управляемой настройки и строгих ограничений нужна
  отдельная нативная интеграция с Config Flow и одним обработчиком отправки.
- Не открывайте этот script встроенному Assist: текущий wrapper не имеет шага
  подтверждения точного номера и текста. Готовность Assist требует отдельного
  ограниченного сценария доступа и проверки подтверждения.
- Ответ Direct API, проверка баланса и HTTP 200 не заменяют подтверждение
  provider delivery receipt или фактического получения.

## Контракт следующего шага для полного issue #17

Обычный HA script выше даёт корректный native action caller, но YAML не может
атомарно резервировать request ID, сохранять ограниченную историю или защищать
от повторной отправки после неоднозначного timeout. Полный вариант требует
небольшого backend handler в собственной интеграции HA, который обязан:

1. принимать ровно один валидированный мобильный E.164 номер и непустой текст;
   лимитировать длину/части сообщения до запроса Direct;
2. проверять локальные лимиты отправки и атомарно резервировать уникальный
   request ID **до** единственного POST; хранить в истории ID, время, состояние
   и UUID, но не телефон, текст или API-ключ;
3. не повторять POST при timeout, transport error, 5xx или невалидном ответе;
   возвращать `unknown`, а UUID/status GET использовать только для сверки;
4. хранить API credential в config entry, никогда не возвращать ключ в форме,
   логах или ошибках; сохранять имя отправителя рядом с настройкой;
5. давать Assist только узкую request/confirm функцию, запрашивать подтверждение
   точного телефона и текста и использовать тот же отправочный handler, что и HA
   action; до такой проверки не expose-ить SMS script помощнику;
6. проверять провайдера отдельно: разрешён ли тестовый аккаунт для номера,
   стоимость, принятый UUID, delivery receipt и получение пользователем. Ни
   баланс, ни HTTP 200 не заменяют этот тест.

Предлагаемые safety defaults из дизайна — не чаще 1 SMS в минуту и максимум
10 SMS в час на запись I-Digital. Это локальные проектные пороги, а не лимиты
провайдера; до реализации их следует проверить на ожидаемом бытовом использовании.
Сообщение о бесплатной отправке на один номер пока основано только на словах
пользователя и не означает, что тестовый аккаунт это разрешает сейчас.
