# Telegram transport worker

The Python backend owns pairing, authorization, deduplication, and agent context. This worker only translates Telegram Bot API updates and outbound send/typing requests over newline-delimited JSON on stdin/stdout. It starts no public listener and does not receive or construct agent prompts.

Run `node /opt/habab-telegram/worker.mjs`. Send one JSON object per line:

- First: `{"type":"configure","token":"..."}`. The token travels only on stdin; it is never emitted or logged.
- Updates: `{type:"ready",username}`, `{type:"message",update_id,chat_id,user_id,message_id,chat_type,chat_title?,text}`, membership-change events, and bounded `{type:"error",operation,code,fatal,request_id?}` events on stdout. `operation` is `configure`, `send`, `typing`, `member`, or `poll`; `fatal` indicates whether the Python bridge should stop this worker. Text such as `/start nonce`, `/new`, `/cancel`, and `/help` is passed through unchanged.
- Incoming text updates wait for `{type:"ack_update",update_id}` on stdin. Python sends this only after an atomic native inbox write and disk readback. Until the matching ACK, the worker does not advance its polling offset; shutdown also releases an outstanding ACK wait. Backend, worker, and vendor library must be delivered together.
- Commands: `{type:"send",chat_id,text,request_id?}`, `{type:"typing",chat_id}`, `{type:"get_chat_member",chat_id,user_id,request_id}`, and `{type:"shutdown"}`.
- Responses: `{type:"sent",request_id?}` only after all chunks were accepted by Telegram, `{type:"member",request_id,status,is_member}` after `getChatMember`, or a bounded error response. Membership API failures return no membership and are fail-closed. Typing and membership failures are nonfatal; configure failures and polling HTTP 409 conflicts are fatal. Error codes contain no raw Bot API response or token.

Text is split at safe Unicode boundaries into chunks of at most 3,800 UTF-16 code units. Outbound Bot API work is serialized; network errors and HTTP 429 are retried at most once, with 429 waits capped at three seconds. Polling uses `getUpdates` long polling with `allowed_updates: ["message", "my_chat_member", "chat_member"]`.

The native text inbox retains queued requests across restart. A request whose handler started but has no completion record requires owner recovery; it is never automatically repeated. The Telegram panel lets the active admin owner confirm cancellation of the displayed pending set without executing it, then resume new requests. A changed snapshot requires a new confirmation. At 256 pending requests per owner/entry/bot, one further update remains unACKed; freeing space automatically persists and acknowledges it while the reader continues handling send/member replies. Completed update tombstones are bounded to 2,000 per scope. Membership metadata and unsupported nontext messages are outside this journal contract.

If an inbox write or disk readback fails, the consumer stays alive and pauses that scope for owner recovery. A failed begin never invokes the handler; a failed completion is retained without repeating its action. The reader also retains an unACKed input and keeps consuming replies when its inbox write fails. After storage is available, the owner can cancel the retained snapshot and admit fresh requests. Recovery cannot discard a currently running turn or control task.

This does not provide exactly-once device actions or a maintenance mute. Startup completion notifications can still send, and installing this version cannot protect updates already acknowledged into an older process's RAM queue. Real Telegram restart/delivery acceptance is separate from the isolated tests. User documentation is prepared for the next release on habab.ru; the current recovery changes have not been deployed to owner-test.

Install dependencies during image build from this directory (`npm ci`). There are no external packages. `npm test` runs the transport unit tests. Group member updates require the bot to be an administrator and `getUpdates` subscribes to `chat_member` and `my_chat_member`; the Python bridge still checks current membership with `getChatMember` before use.
