# Telegram transport worker

The Python backend owns pairing, authorization, deduplication, and agent context. This worker only translates Telegram Bot API updates and outbound send/typing requests over newline-delimited JSON on stdin/stdout. It starts no public listener and does not receive or construct agent prompts.

Run `node /opt/habab-telegram/worker.mjs`. Send one JSON object per line:

- First: `{"type":"configure","token":"...","telegram_transport":{"mode":"direct"}}`. The token travels only on stdin; it is never emitted or logged.
- Updates: `{type:"ready",username}`, `{type:"message",update_id,chat_id,user_id,message_id,chat_type,chat_title?,text,voice?}`, membership-change events, and bounded `{type:"error",operation,code,fatal,request_id?}` events on stdout. `operation` is `configure`, `send`, `typing`, `member`, or `poll`; `fatal` indicates whether the Python bridge should stop this worker. Text such as `/start nonce`, `/new`, `/cancel`, and `/help` is passed through unchanged.
- Incoming text and voice updates wait for `{type:"ack_update",update_id}` on stdin. Python sends this only after an atomic native inbox write and disk readback. Until the matching ACK, the worker does not advance its polling offset; shutdown also releases an outstanding ACK wait. Backend, worker, and vendor library must be delivered together.
- Commands: `{type:"send",chat_id,text,request_id?}`, `{type:"typing",chat_id}`, `{type:"get_chat_member",chat_id,user_id,request_id}`, and `{type:"shutdown"}`.
- Responses: `{type:"sent",request_id?}` only after all chunks were accepted by Telegram, `{type:"member",request_id,status,is_member}` after `getChatMember`, or a bounded error response. Membership API failures return no membership and are fail-closed. Typing and membership failures are nonfatal; configure failures and polling HTTP 409 conflicts are fatal. Error codes contain no raw Bot API response or token.

Text is split at safe Unicode boundaries into chunks of at most 3,800 UTF-16 code units. Outbound Bot API work is serialized; network errors and HTTP 429 are retried at most once, with 429 waits capped at three seconds. Polling uses `getUpdates` long polling with `allowed_updates: ["message", "my_chat_member", "chat_member"]`.

In a linked family group, the Python bridge accepts text only when it starts with standalone `Ко` or `Эй дом` (case-insensitive), or mentions the actual bot username. It strips the invocation before sending the request to the shared assistant session. Group controls also need an address, for example `Ко /help` or `/cancel@bot_username`. The `/start nonce` linking handshake keeps its separate authorization. Ordinary family conversation and empty invocations do not reach the assistant.

The native text inbox retains queued requests across restart. A request whose handler started but has no completion record requires owner recovery; it is never automatically repeated. The Telegram panel lets the active admin owner confirm cancellation of the displayed pending set without executing it, then resume new requests. A changed snapshot requires a new confirmation. At 256 pending requests per owner/entry/bot, one further update remains unACKed; freeing space automatically persists and acknowledges it while the reader continues handling send/member replies. Completed update tombstones are bounded to 2,000 per scope. Voice updates retain bounded file metadata in this journal; audio bytes and transcripts are not stored by the inbox. Membership metadata and other unsupported message types are outside this journal contract.

If an inbox write or disk readback fails, the consumer stays alive and pauses that scope for owner recovery. A failed begin never invokes the handler; a failed completion is retained without repeating its action. The reader also retains an unACKed input and keeps consuming replies when its inbox write fails. After storage is available, the owner can cancel the retained snapshot and admit fresh requests. Recovery cannot discard a currently running turn or control task.

Inbox durability alone does not provide exactly-once device actions or a maintenance mute. Without the explicit startup mode below, completion notifications can still send, and installing this version cannot protect updates already acknowledged into an older process's RAM queue. Real Telegram restart/delivery acceptance is separate from the isolated tests. User documentation is prepared for the next release on habab.ru; the current recovery changes have not been deployed to owner-test.


## Recorded voice messages

The bridge accepts recorded voice in authorized private chats, up to 120 seconds and 5 MiB. Group voice messages are ignored. The worker emits the file ID, duration, optional size and MIME type; the Python bridge checks access before requesting the file. It downloads OGG through the configured Telegram route, including an explicit per-bot proxy or the Habab relay. Both reported size and downloaded bytes are bounded. Downloads and transcription have deadlines, and cancellation or revoked access prevents the transcript from starting an assistant request.

With Habab selected, the bridge requires the relay's `getFile`, `telegram.voice` and `speech` capabilities, downloads through `/telegram/downloadFile`, and posts recorded audio to `/v1/audio/transcriptions`. The gateway uses its configured Gemini voice key and fixed audio model; it returns `{text}`. The transcript enters the existing private assistant session, and replies use Telegram text messages. Direct OpenAI and Gemini providers use their selected key for speech; DeepSeek has no recorded-speech endpoint. A failed selected route returns an error without switching to another provider or a direct Telegram connection.

Source tests cover event parsing, ACL, route selection, proxy use, size limits, empty or failed transcription, cancellation and revoked access. Real Telegram delivery, relay audio recognition and device actions need acceptance on the target installation.

## Explicit cold-start maintenance (source preview)

Before starting Core with this version, an operator can create the empty file `.habab-telegram-maintenance` in the Home Assistant configuration directory (`/config/.habab-telegram-maintenance` in this Docker distribution). An absent marker preserves normal behavior. Maintenance startup registers the administrative API but does not load/replay the Telegram inbox, resolve transport, create a worker, validate credentials, read/ACK updates, or send messages, typing, and membership requests. The protected status response contains `maintenance: true` and `error: "telegram_maintenance"`. Startup notification callbacks leave completion records pending. Bot settings and bindings are retained.

The worker receives the marker path in `HABAB_TELEGRAM_MAINTENANCE_FILE` and also checks it before accepting configure/send/poll work. A standalone worker defaults to `/config/.habab-telegram-maintenance`. The file's contents are not read. Removing it does not hot-resume either process: remove it before a separately authorized later Core startup to return to normal behavior. Normal startup can then poll and deliver pending completion notifications; uncertain local requests still require owner recovery.

This is a startup guard for the Habab Telegram integration, not a host-wide Telegram firewall or a hot-pause/drain operation. It does not stop unrelated bots/integrations, cancel an already accepted outbound request, or protect the old version's acknowledged RAM queue during its shutdown. Enabling the marker for a future startup does not by itself prove an end-to-end message-free first restart. Unconfirmed Telegram updates remain subject to Telegram's 24-hour retention limit. The mode has only isolated source tests; no owner-test restart or real Telegram acceptance has been performed.

Install dependencies during image build from this directory (`npm ci`). There are no external packages. `npm test` runs the transport unit tests. Group member updates require the bot to be an administrator and `getUpdates` subscribes to `chat_member` and `my_chat_member`; the Python bridge still checks current membership with `getChatMember` before use.
